# Headless apps: HeadlessKit, its protocol, and scenarios

HeadlessKit lets an agent or a test operate a real app **without its UI**. It sends commands and reads JSON back. The app runs its real models, persistence and backends.

**What it is, exactly.** HeadlessKit is a machine-operable projection of the app's user-facing state and capabilities, backed by the app's real state and operations. It describes **screens** and the **user actions** each screen offers right now. It does not replace only the views: whatever a view does itself is either reproduced by the adopter or left out, and each such case is a named difference (see [ML Browser's differences](#differences-from-the-app)). Adopting it should move behavior out of views rather than reproduce it in adapters, wherever that is practical.

ML Browser is the first adopter; the app integration is tracked in AIA-0970 (#970). The package is app-agnostic: any SwiftUI app can adopt it.

## Purpose and design principles

The main purpose is a **fast verification loop for agents**: an agent changes the app, builds it, and checks the result through the same screens and actions a user has, in seconds per step rather than through a UI test. Scenarios reuse the same loop for end-to-end tests.

- **One operation is one meaningful user intention**, such as `sign-in` or `save`, not a tap. It returns once its effect has landed, with enough to choose the next operation.
- **Every response is complete:** `route`, `state`, `actions` and `context`. A client never needs a second request to learn where it is or what it can do.
- **An action name means something only on the screen that offers it.** `close` on `findings` and `close` on `drawer` are different actions. An action that is absent is not available, and the list of offered actions is the authority on that.
- **The user-equivalence rule.** If the headless interface can do something, a user could have caused the equivalent operation. The exceptions, each with how to remove it:
  - `save` stores and uploads the **whole staged image**, with no viewport crop. Remove it by giving `save` a nominal viewport, so the save sheet's own framing and crop run (`FindingCapture.cropped(to:)` returns the image unchanged for the unit rect it is given now).
  - `detect-image` detects on a **staged file**, not a page the browser loaded. Remove it by detecting through an offscreen `WKWebView` (the phase 3 roadmap in #970).

### Rejected designs

- **`unavailableBecause`** (a reason attached to each action that is not offered): an absent action stays the authority. A reason list would be a second, drifting description of the same state.
- **A `HeadlessSnapshot` type**: responses are already atomic (see [Atomicity](#protocol-v1)), so a separate snapshot adds nothing.
- **`ifRevision`** (a request that fails when the state changed since a given response): the single controller planned in #992, together with the rule that an action name means something only on the screen that offers it, covers the races it would guard against.
- **Moving `loadProducts` out of the views**: scenarios would then depend on the StoreKit sandbox network (#970, 2026-09-27).
- **A general `not` expectation**: `not equals` on a misspelt pointer always holds, so a typo would silently pass or, in `unless`, silently skip. `notRoute` covers the case that needs negation and is route-checked.

### Developing against a local checkout

To change the kit and the app together without a release, point both consumers at a local clone:
- **The app:** drag the clone's folder into the workspace in Xcode's navigator. The folder must be named `HeadlessKit`: a local package's identity is its directory name, and a clone under another name fails resolution with "doesn't match override's identity". With the same identity it overrides the pinned one in every build of the workspace, Xcode's and `xcodebuild`'s (`unittest.sh`, `headless.sh build`), for as long as the reference is there. Adding it edits a checked-in file (`contents.xcworkspacedata`), so remove the reference before you commit and check that it and the `Package.resolved` files are unchanged.
- **Tools:** `swift package --package-path Tools edit --path <absolute path to the clone> headlesskit` makes `swift run --package-path Tools ProjectTool headless …` build against the clone. While it is edited, SwiftPM drops the pin from `Tools/Package.resolved`, so `HeadlessKitPackageTests`, and with it `unittest.sh`'s first step, fails on purpose: an edited resolution must not be committed. Unedit before the sweep and before you commit. `swift package --package-path Tools unedit headlesskit` restores the pin.

## Adopting it in an app

1. Implement `HeadlessApplication` over your existing state objects. `currentScreen()` must **derive** the screen from app state on every call. A separate navigation stack would drift from the app.
2. Implement one `HeadlessScreen` per screen. `state()` returns redacted JSON. `actions()` returns only what a user could do here now; leave out anything the UI disables.
3. Each `HeadlessAction` handler calls **the same model methods the UI calls**. When a view does the work inline, move that work into the model first and have the view call it too. A handler returns once its effect has landed, by awaiting a readiness signal or `HeadlessWait.until`, never a fixed delay.
4. Declare transitions with `navigatesTo`. `goto <route>` only follows a transition the current screen offers, so a client cannot reach a screen a user could not. The session fails an action whose declared transition does not arrive.
5. Offer named `WaitCondition`s for effects that finish later, such as "model loaded". The built-in `route` condition always exists.
6. Optionally declare `navigationMap` (default `NavigationMap.empty`): every route with a one-line summary, and the transitions that can leave it as `TransitionDeclaration(action:to:condition:)`. A `nil` action means the app moves there on its own. Declare only moves to another route; an action that stays on its route is not a transition. With a map, the session answers `map`, the handshake lists the routes, and `goto` and `wait route=` reject an undeclared route (see the protocol below). An app without one behaves as before.
7. In a **debug-only** launch mode, serve the application. A SwiftUI app puts HeadlessKitUI's `.headless(when: HeadlessLaunch.isRequested) { … }` on its window's root view, inside `#if DEBUG`, or uses `HeadlessServerView { … }` as the content of a separate headless `App`, as ML Browser does. Either starts one `HeadlessServer` for the process and publishes its endpoint to `HeadlessEndpoint.defaultFile`; anything else starts `HeadlessServer(session:endpointFile:)` itself. The server cannot be in a release build: since kit 0.2.0 the server, like the rest of the kit, compiles to nothing there, provided nothing in the app's package graph enables the `HeadlessHost` trait (see [zero Release footprint](#products-the-headlesskit-package)). Keep your own headless files under `#if DEBUG` as well. A listener has no place in a shipped app (see [what the token protects](#protocol-v1)).

```swift
@MainActor final class MyHeadlessApp: HeadlessApplication {
	let model: AppModel
	init(model: AppModel) { self.model = model }
	func currentScreen() -> any HeadlessScreen { model.isSettingsShown ? SettingsScreen(model: model) : HomeScreen(model: model) }
}

@MainActor struct HomeScreen: HeadlessScreen {
	let model: AppModel
	var route: Route { "home" }
	func state() -> JSONValue { ["items": .array(model.items.map { ["id": .string($0.id)] })] }
	func actions() -> [HeadlessAction] {
		[HeadlessAction("open-settings", summary: "Open Settings.", navigatesTo: "settings") { [model] _ in
			model.showSettings()   // the method the Settings button calls
			return nil
		}]
	}
}
```

## Protocol v1

The protocol is JSON Lines over TCP on `127.0.0.1`: one JSON document per line, with keys sorted.

1. **Handshake.** The client sends `{"hello":{"protocolVersion":1,"token":"…"}}`. The server replies `{"hello":{"protocolVersion":1,"metadata":{…},"routes":[…]}}`, or sends `{"error":{…}}` and closes on a wrong token (`unauthorized`), a wrong version (`protocolMismatch`), or while another client drives the app (`busy`, see Ordering). `routes` lists the routes the app declares, in declaration order, and is absent when it declares no navigation map.
2. **Requests.** Requests are flat and carry an `id`:

   ```json
   {"id":"1","command":"state"}
   {"id":"2","command":"perform","action":"enable","arguments":{"id":"…"}}
   {"id":"3","command":"goto","route":"drawer"}
   {"id":"4","command":"wait","condition":"route","arguments":{"route":"home"},"timeout":30}
   ```

   The other commands are `help`, `actions` and `map`. Since kit 1.0.0 `actions` has no `Command` case of its own: the wire word is still accepted and answers like `state`, whose response lists the actions. Arguments are validated against the action's parameters before the handler runs. Unknown names and wrong types are rejected. **Types are strict (AIA-0992):** a `string` parameter takes a JSON string, `integer` an integral number, `number` a finite number, `boolean` `true` or `false`. Text such as `"3"` or `"true"` for a typed parameter is `invalidArgument`, and so is `7` for a string. Converting command-line text is the command line's job: `headless.sh exec` reads the declared types first (see Tooling).
3. **Responses.** Every response carries `id`, `ok`, `route`, `state`, `actions`, `context`, an optional `result`, and an optional `error` of the form `{code, message}`. App-level failures are responses, not dropped connections. Error codes: `malformedRequest`, `unknownCommand`, `unknownAction`, `unknownCondition`, `unreachable`, `invalidArgument`, `actionFailed`, `undeclaredTransition`, `timeout`, `unauthorized`, `protocolMismatch`, and `busy` (hello only). Codes are an open set.
4. **Ordering.** Commands run one at a time, and each connection is answered in request order.
   - **One controller (AIA-0992).** One client drives the app at a time: the connection that completed its hello and still sends requests. A hello while there is one gets `{"error":{"code":"busy",…}}` and the connection is closed. There are no observer-only connections, because a read is a render (below).
     - A connection that has not sent its hello never holds the slot, so a stalled socket cannot lock the controller out; it is closed after the handshake timeout.
     - A client gives the slot up as soon as it stops sending: it closes, its end of stream arrives, its socket fails, or it breaks the protocol. Commands it already sent still run first, because each is queued in the session as it arrives; the next client's commands wait behind them. So a client that abandoned a long `wait` frees the slot at once, but the next client's first command runs only once that wait ends (at most 600 s); give it a request timeout to match. `HeadlessClient.close()` half-closes and waits (at most a second) for the server to close its side, so a client that connects right after another closed is not refused.
     - A client that keeps its socket open keeps the slot, even while idle. A killed client's socket is closed by the system; a client stuck mid-`wait` with its socket open holds the slot until it disconnects (`down`, then `up`, is the way out).
     - `busy` fails fast: nothing retries it. So `headless.sh exec` against an installation a running `headless.sh test` drives is refused, which is intended. Two installations are two processes and never block each other.
   - **Atomicity.** A response's snapshot is built in one MainActor turn once the command has finished: `HeadlessSession`'s `snapshot` is synchronous and `@MainActor`, and reads `currentScreen()` once for `route`, `state` and `actions`, then `context()`. The command itself may span turns: a `perform` or `wait` suspends while its effect lands. Nothing promises the state stays that way after the response: the app keeps running.
   - **An action name is scoped to its screen.** A name means something only on the screen that offers it: `close` on `drawer` and `close` on `findings` are different actions. Between reading `actions` and sending `perform`, the app may move on its own; the session then resolves the name on the new screen. So an adopter must never offer the same name on two routes where one can follow the other through moves the app makes on its own (action-less edges of the map, one or several): the request then fails with `unknownAction` instead of running another action. ML Browser's `HeadlessNavigationMapTests` and `HeadlessWalkTests` assert it, over the declared names, the names each walked screen offers, and the back-up question's.
   - **A read is also a render.** An adopter's `currentScreen()` and `context()` may settle what a view would have settled on screen. ML Browser runs its root gate's `reconcile()` in both, so `state` can raise a Welcome screen or start the tour exactly as rendering would. Once settled, repeating a read changes nothing.
5. **The navigation map (AIA-0982).** `{"id":"5","command":"map"}` answers with the app's declaration in `result`, marked `"guarantee":"possible"`: a declared transition **can** happen when its condition holds. It is **not guaranteed** to be offered now.
   - `current` is the current route. `routes` lists every declared route in declaration order as `{route, summary, current, transitions}`, and each transition as `{action, to, condition}`. A transition without `action` is one the app makes on its own.
   - On the current route only, a transition is marked `"open": true` when the screen offers its action now and that action's `navigatesTo` is the transition's target. It is marked `"available": true` when the screen offers the action with no `navigatesTo`, so the destination is decided when it runs (the ML Browser's `welcome` `continue`). Every other edge says what is possible, not what the screen offers.
   - `undeclared` lists the current screen's live transitions (`{action, to}`, from `navigatesTo`) that the map lacks: drift in the declaration. It is advisory; what the session enforces is where an action lands (item 7).
   - An app that declares no map answers with an empty `routes` and an empty `undeclared` array: there is no declaration to drift from.
6. **Undeclared routes (AIA-0983).** When the app declares a map, `goto` or `wait` with `condition: route` naming a route outside it fails at once with `invalidArgument`: `unknown route 'hme'; did you mean 'home'? (known: …)`. Before, the same request failed with `unreachable`, or waited out its whole timeout. An app that declares no map keeps that behavior.

7. **Declared transitions (AIA-0994).** After every action (`perform`, and `goto`'s), the session checks where the app landed against the map. Let hop1(S) be the targets of the action-less edges out of the routes in S: **one** of the app's own moves, never more. A transitive closure would accept `drawer` `close` doing nothing, via home → paywall → drawer.
   - **(i)** The action declares `navigatesTo` t: it may land on {t} ∪ hop1({t}), but not on its origin.
   - **(ii)** Otherwise, when the map declares edges for this route and action: on their targets ∪ hop1(targets), but not on the origin.
   - **(iii)** Otherwise: on {origin} ∪ hop1({origin}). An action without an edge stays on its screen, or the app moves once on its own.
   - A declared transition that does not move is always a failure: sheets have no inbound app moves, `sign-in` and `save` close their sheet before they return, and a handler that fails throws before the check runs.
   - A miss fails with **`undeclaredTransition`**, distinct from `actionFailed`: the operation did not fail, the app went somewhere undeclared. Example: `'close' on 'drawer' landed on 'drawer'; declared: home; accepted after the app's own moves: paywall, consent, backup-consent`. Tier (iii) says `declared: none (stays on 'drawer')`.
   - An app with an empty map keeps the check it had: only a set `navigatesTo`, exactly. Its code changes from `actionFailed` to `undeclaredTransition` (see Compatibility).
   - `HeadlessSession(appMoves:)` is `.oneHop` by default; `.off` accepts only what is declared, for auditing a map. The kit's `HeadlessLaunch` reads it from `-headlessAppMoves off`, which only `headless.sh test --app-moves off` or `up --app-moves off` passes, never a scenario; ML Browser echoes it as `launchOptions.appMoves`.
   - **What the rule can catch.** Around `home` and `drawer` it is broad: any tier-(ii) action that declares `home` or `drawer` accepts about {home, drawer, paywall, consent, backup-consent}, because the app can raise the paywall, the consent question or the back-up question over either. For example, removing one `sign-in` exit does not fail a run, since every `sign-in` exit is one app move from another. Its teeth are the sheets, the onboarding routes (`gate`, `welcome`, `tour`) and the origin. The closure-off audit (below) catches the rest.

   None of this bumps `HeadlessProtocol.version`. An older client ignores `routes` in the hello, an older server answers `map` with `unknownCommand`, and the rejection only changes the error of a request that could never succeed.

`HeadlessServer` binds an ephemeral port. It writes `{host, port, token}` atomically, with mode `0600`, to the endpoint file, and removes the file on `stop()`. A killed app cannot remove its file, so a launcher must not treat the file as proof that the app is running. `HeadlessClient` reports a refused connection as `notRunning`: the app is not running, or was suspended. A connection that sends no valid hello within 10 seconds is closed.

**What the token protects.** Loopback is reachable by every local process. The token (256 random bits, compared in constant time) keeps out processes that cannot read the endpoint file. That guards against accidental or ordinary local access, such as another tool probing ports. It is **not** a boundary against code running as the same user, which can read the file. The safety boundary is elsewhere: the server exists only in debug builds, and ML Browser's production locks (see [Never production](#ml-browsers-headless-mode)) keep automation away from production data.

## Scenarios (schema v1)

A scenario is a JSON file. Decoding is strict: an unknown key anywhere is an error, so a typo cannot silently assert nothing.

```json
{
  "schemaVersion": 1,
  "name": "enable-a-model",
  "installations": { "a": { "launch": { "flags": { "isPaymentsEnabled": true, "isFreeAccessPeriodEnabled": true, "isAnalyticsEnabled": true, "isCrossDeviceAnalyticsIdentityEnabled": false } } } },
  "steps": [
    { "on": "a", "wait": { "condition": "ready", "timeout": 120 }, "expect": [ { "route": "welcome" } ] },
    { "on": "a", "perform": { "action": "continue" }, "expect": [ { "route": "tour" } ] },
    { "on": "a", "perform": { "action": "skip" }, "expect": [ { "route": "consent" } ] },
    { "on": "a", "perform": { "action": "deny" }, "expect": [ { "route": "home" } ] },
    { "on": "a", "goto": "drawer", "capture": { "model": "/state/models/0/id" } },
    { "on": "a", "perform": { "action": "enable", "arguments": { "id": "${model}" } },
      "expect": [ { "equals": { "pointer": "/state/models/0/enabled", "value": true } } ] },
    { "on": "a", "relaunch": true, "expect": [ { "route": "home" } ] }
  ],
  "teardown": []
}
```

- **`installations`** are independent copies of the app, each with its own data. `launch` is opaque to the runner; the adopter's `InstallationLauncher` interprets it.
- A **step** does at most one of `goto`, `perform`, `wait` or `relaunch`. A step with none of them observes the current screen. `on` is required when there are several installations.
- **`expect`** accepts `route`, `notRoute` (the app is on any route but the one named), `equals`, `exists`, `absent`, `matches` (a regex against a string), and `error` (the command must fail with that code). Pointers address the response document: `/route`, `/state/…`, `/context/…`, `/result/…`, `/error/code`. A response carrying an error fails the step unless an `error` expectation names it.
- **`capture`** maps a variable to a pointer. Later steps use `${variable}`. A string that is exactly `${variable}` keeps the value's JSON type. `${env:NAME}` reads the runner's environment. Credentials belong there, never in a scenario file. In a `matches` pattern, a substituted value is matched literally, never as regex syntax.
- The **runner** launches the installations, runs the steps in order, stops at the first failure, always runs `teardown` (continuing past teardown failures), and terminates what it launched. The `ScenarioReport` lists every failed expectation and keeps the full response of a failed step.
- **Route check (AIA-0983).** After the handshakes and before step 1, the runner checks every literal route the scenario names against the routes its installation declared: `goto`, `wait` with `condition: route`, `route` and `notRoute` in `expect`, and the same two in a teardown step's `unless`, in steps and teardown.
  - A mismatch runs no step. The run fails with a setup failure listing one line per offending step, each naming the step and suggesting the closest declared route. Teardown and termination still run.
  - An installation's steps from its first `relaunch` on, teardown included, are left out of this check: the relaunched process may be another build, so the check before each step judges them against its handshake.
  - Before each step is sent, its resolved routes, `${…}` values included, are checked again against the installation's latest handshake, so a relaunch into another build is checked against that build. This includes `expect route`, which is compared locally and would never reach the app's own check.
  - An installation whose app declares no routes is not checked.
  - **Static check.** `headless.sh test --lint [files…]` runs the same check with no build and no simulator, against a checked-in copy of the app's map (see [ML Browser's navigation map](#ml-browsers-headless-mode)). Plain `headless.sh test` runs it first, before building or launching anything. A scenario that fails it or does not load is reported and counted as failed, and does not run; the others still build and run. Only when no scenario remains is nothing built. Both forms must run from the repository root, and say so before reading the map when they do not.
    - The checked-in map can lag a freshly changed declaration. It then blocks the affected scenarios before the build, even though the new build would accept them. The fix is to regenerate the file from the failing `HeadlessNavigationMapTests` equality test (see [Keeping it equal](#ml-browsers-headless-mode)).
    - It is an early filter: the running app's handshake is authoritative, and the runner checks the routes again after each launch, against what that build declares.
  - **How fast a typo fails.** `--lint`, the pre-build check and the session's rejection of a `goto` or `wait route` each fail within a second. The runner's post-launch check runs only after the simulator launch, which takes 30–120 seconds.
- **`bestEffort`** (teardown only): `"bestEffort": true` turns the step's failure into a warning instead of a failed run. Use it for cleanup that must be attempted from wherever a failed run stopped. It is never silent: the report lists it under `warnings`, its step carries `"bestEffort": true` in the report's JSON, and `headless.sh test` prints it as `warning:`. The decoder and `validate()` both refuse it outside `teardown`, so it cannot weaken a step's assertions. An ordinary teardown step that fails still fails the run.
- **`unless`** (teardown `perform` steps only, AIA-0990): `"unless": [expectation…]` skips a cleanup that has nothing to do, so that a green run does not warn about it and a warning keeps its meaning. For example, `sign-out` `unless` `{"equals": {"pointer": "/context/auth/accountPresent", "value": false}}`.
  - Just before the step, the runner reads the installation's `state`. That is one extra round trip, and on an app that no longer answers, one more client timeout. A read is also a render; see [Atomicity](#protocol-v1). If **every** expectation holds for that response, the step is not sent and is reported as **skipped**: `"skipped": true` in the report's JSON, listed under `skipped`, and printed by `headless.sh test` with its own mark, `–`, never as a warning. A skipped step has no failures.
  - `unless` is decided before the step's own command is resolved, so a step with nothing to do is skipped even when its arguments name a value that a failed run never captured.
  - On any doubt, the step runs as written: an expectation that does not hold, a read that fails or answers with an error, a `${…}` that cannot be resolved, a route the app does not declare, or any route at all when the app declares none (a misspelt `notRoute` would then always hold). A predicate is never the reason a cleanup was not attempted. When the step then fails, its report also says why `unless` could not be decided.
  - Use predicates that fail safe on a typo: `equals` (a wrong pointer or value never equals) and `notRoute` (route-checked, so a misspelt route fails `--lint` and the setup check). A negated `matches` pattern, such as `^(?!consent$)`, holds on a misspelling and would silently skip the step; don't use one.
  - The decoder refuses `unless` outside `teardown`. `validate()` also refuses it on a step that is not a `perform`, when it is empty, when it holds an `error` expectation, when a pointer in it contains `${…}` (pointers are never substituted, so `absent` would always hold), or beside a `capture` (a skipped step would capture nothing).
  - A route predicate sees only the top screen. A save sheet under a pending tour reads as `tour`, and a pending back-up question under a sheet reads as that sheet. So the ML Browser teardowns order `deny`, `cancel`, `close`, `decline`: each one uncovers the next.
  - `unless` and `bestEffort` combine: a step whose `unless` holds is skipped without a warning; one whose `unless` does not hold runs, and its failure is a warning.
- **Compatibility within a version.** Compatibility within a schema version is **backward only**: a newer runner accepts every file an older one accepted, with the same meaning. There is no forward compatibility, because decoding is strict: an older runner rejects a file that uses a newer optional key, such as `bestEffort` (before AIA-0974) or `unless` and `notRoute` (before AIA-0990). A change that alters the meaning of an existing file bumps `schemaVersion`.
- **The report.** `ScenarioReport` is `Codable`. Its JSON form carries every step's `failures`, `bestEffort` and `skipped`, which the package tests check. `headless.sh test` prints the report as text and writes no report file; there is no JUnit output.

## ML Browser's headless mode

Headless mode is a launch mode of ML Browser's Debug app (AIA-0991; until then, AIA-0970's separate headless build). Launched with `-interface headless`, the app runs without its UI:

```sh
scripts/headless.sh build          # or ./scripts/unittest.sh, which makes the same build
scripts/headless.sh up --state a   # installs it on aia-headless-a and launches it with -interface headless
```

- **Same app.** `AppEntry` launches `MLBrowserHeadless` instead of `MLBrowser`. It keeps the same app delegate, bootstrap and `AppRuntime`, and the same composition root. The one window is HeadlessKitUI's `HeadlessServerView`: a status line, and the `HeadlessServer` it owns for the life of the process, answering in place of the views. The entry keeps only what is ML Browser's: the free-access seed before bootstrap, the development-backend refusal, and logging; the flag pins and staged images are `HeadlessLaunchOptions`'. What the views did themselves is either reproduced by the adapters or left out; [Differences from the app](#differences-from-the-app) lists each case.
- **Which builds share one binary.** `headless.sh build` is the build half of `./scripts/unittest.sh`: `xcodebuild build-for-testing -testPlan MLBrowserUnitTests` with `AIA_INCLUDE_TEST_FIXTURES=YES`, in `unittest.sh`'s DerivedData (`.deriveddata`, or `DERIVED_DATA_PATH`; `SPM_CACHE_PATH` as there). Its destination is `aia-headless-a` by id instead of the unit tests' iPhone, which changes only asset thinning.
  - Measured on AIA-0991: after the unit tests, `headless.sh build` compiles no Swift and links nothing; the app executable and `ML Browser.debug.dylib` keep their UUIDs. The UI plan and the `HeadlessParity` plan, run with the same flags into the same DerivedData, reuse that product the same way. So the unit tests, the UI tests, the parity plan and headless mode run one binary.
  - `build-for-testing`, not `build`: the test build links the package products (HeadlessKit, SupportLogFormat, NativeModelConverter) into the app as frameworks it shares with the test bundle, while a plain `build` links them statically, and each relinks the other's app.
  - **Not the product of Xcode's Run button.** Run builds the scheme's `build` action into Xcode's own DerivedData, without the fixtures flag. It compiles the same Swift in the same configuration (the flag only adds bundle resources, below), but it is another binary: the package products are linked statically, and it carries no FastViT fixture. Headless mode runs from it too: see [Debugging headless mode in Xcode](#debugging-headless-mode-in-xcode).
  - Every build into the shared DerivedData must pass `AIA_INCLUDE_TEST_FIXTURES=YES`: the fixture phase removes the fixture from a build without it, and `up` installs whatever product is there. A build with other settings replaces the product too: `scripts/slopguard-baseline.sh`'s coverage build (`-enableCodeCoverage YES`) builds into the same DerivedData, so the next `headless.sh build` recompiles.
  - The fixture must be fetched first; `embed_apple_test_models.sh` fails the build without it. `headless.sh build` runs `scripts/fetch_apple_test_models.sh` first, as `unittest.sh` does.
  - Never run `headless.sh build` or `test` while `unittest.sh` or a UI test run uses the same DerivedData. `build`, and `up` or `test` before they install, refuse while another `xcodebuild` names that DerivedData; `up` and `test` also refuse a product built for any backend but development. After `unittest.sh`, `headless.sh test --no-build` and `up` use its product directly; a no-op `headless.sh build` still costs about 20 s of script phases and signing.
  - `.deriveddata-headless`, the old separate build's DerivedData, is no longer used and can be deleted by hand.
- **What selects it.** `-interface headless`, a key/value pair: a bare flag would take the next argument as its value. `AppInterface.resolve` reads it through the kit's `HeadlessLaunch`, which parses `-interface` and `-headlessAppMoves` and refuses an XCTest host, and adds ML Browser's rules, the development backend and `UI_TESTING`. It exists only in Debug builds:
  - Only a build for the development backend reads it. There, the last `-interface` wins; `-interface ui`, or none, is the app. A missing value, a value starting with `-`, or any other value stops the launch, as the old build setting refused any value but `ui` or `headless`. So does `headless` in a test host (`XCTestConfigurationFilePath` or `UI_TESTING`), because the scheme hands its launch arguments to the tests.
  - A Debug build against production **ignores** `-interface` unread and launches the app: the entry point and the server are not compiled into it, so there is nothing to select and nothing a value could stop.
  - A Release build contains no code that reads `-interface`.
  - A UI launch never parses the headless launch options below, so a stale one cannot stop it.
- **Real composition.** Headless mode uses what a Debug build uses: Clerk's development instance, the development findings backend, ConfigCat's Test environment, and persistent storage. Each simulator device is one installation of the app. The bundle also carries the unit tests' FastViT fixture (a [Differences](#differences-from-the-app) row).
- **Launch options.** Pass them as launch arguments. Each is echoed in the handshake `metadata` and in `context`.
  - `-headlessFlag key=true|false` is repeatable and pins a feature flag over the live provider (below).
  - `-headlessStagedImage <name>` is repeatable and names an image the launcher staged (below). Only the name is passed, never a host path, and `launchOptions.stagedImages` echoes it.
  - `-headlessFreeAccessEndsIn <seconds>` (30…3600; Debug only, AIA-0984) seeds a free-access window that ends that many seconds after launch, with its day-0 Welcome screen marked shown, and `launchOptions.freeAccessEndsIn` echoes it. A scenario sets it with the launch key `"freeAccessEndsIn": <seconds>`, and `up` with `--free-access-ends-in <seconds>`.
    - Why it exists: the parity flow in which the paywall arrives over an open sheet needs access to run out while the app is in use, and a real window lasts calendar days. Only the anchor is seeded; `FreeAccessState`'s own expiry wake-up ends access and the root gate walls, as for a user.
    - What it touches: `FreeAccessExpirySeed` writes the fast store only, and only when neither store holds an anchor. A relaunch that passes it again keeps the window it opened, and an existing install is never re-anchored. The next reconciliation copies the record into the Keychain, as it repairs any store missing the other's anchor. The UI tests' `freeAccessEndsInSeconds` uses the same seed.
    - How to remove it: delete `FreeAccessExpirySeed`, this option, `UITestLaunchConfiguration.freeAccessEndsInSeconds`, the launch key and `parity-paywall-over-sheet.json`.
  - `-mockSubscription subscribed|notSubscribed` replaces StoreKit with the mock. It is for manual `up` only, and **no committed scenario may use it**: `HeadlessScenarioPolicyTests` in the ProjectTool tests fails if one does.
    - Why it still exists: without it headless mode runs real StoreKit (AIA-0976). Under `simctl launch`, with no scheme StoreKit configuration, the app checks its entitlements against the sandbox and reads as not subscribed. (The gating probe also fetched the real product from the sandbox; headless mode itself never fetches products, see the gaps below.) A *subscribed* install would need a real sandbox purchase, which automation must not make, and there is no supported way to apply a `.storekit` file to a `simctl`-launched app. The mock is the only way to look at a subscribed install headlessly.
    - How to remove it: when a subscribed state can be reached without a purchase, for example through a supported StoreKit test configuration for launched apps.
- **Flag pins (AIA-0976).** Every scenario pins the four **entry flags**, which decide how a fresh install gets into the app. Everything else follows ConfigCat's Test environment unless a scenario is about it. `HeadlessScenarioPolicyTests` fails a scenario that leaves an entry flag unpinned.
  - `isPaymentsEnabled`: launch-captured. A fresh install has no mirrored value, so its first launch captures whatever the snapshot holds at that moment (the compiled default `false`, or the fetched Test value), and its relaunch captures the mirrored Test value. Unpinned, one scenario could meet the introduction on its first launch and the paywall or a free-access window after `relaunch`.
  - `isFreeAccessPeriodEnabled`: launch-captured, with the same first-launch race. It decides between the free-access Welcome screen and the wall.
  - `isAnalyticsEnabled`: live, not captured. A Test-environment change mid-soak removes the consent question from every scenario at once.
  - `isCrossDeviceAnalyticsIdentityEnabled` (`false`, except `sign-in-sign-out`): with it on, the consent question waits for Clerk's session check, so `deny` right after `skip` races Clerk. Only `sign-in-sign-out` pins it on, because it asserts the account's own question.
  - Evidence for the race: on 2026-09-27 an unpinned fresh install on `aia-headless-b` reported `isPaymentsSurfaceEnabled: true, freeAccess: open`, the Test values, while the compiled default for payments is `false`. Which one a first launch captures depends on fetch timing.
  - A dedicated ConfigCat environment for automation would let the entry pins go. That needs a new environment and SDK key, so it is deferred to the owner.
- **Staged images (AIA-0975).** A scenario's `launch` block may list repository files under `"stage": ["ios/…/image.png", …]`, and `headless.sh up` takes `--image <path>` (repeatable) for the same thing.
  - ProjectTool accepts only a relative path that resolves inside the repository, with symlinks resolved on both sides and compared by path component. The file must be a regular `.png`, `.jpg` or `.jpeg`, and no two entries may share a name.
  - Before every launch it copies each file into `Library/Application Support/Headless/Staged/<name>` in the app's data container.
  - Nothing is downloaded at run time. The picture stands in for the page snapshot the web screen detects on; browsing stays out of scope.
  - The scenarios use `ios/MLBrowserUnitTests/Fixtures/terrain_iphone.png`, an existing unit-test fixture from AIA-0306 whose source is not recorded. It is a grayscale terrain hillshade with no people, text or personal data. It is staged into local simulators and uploaded only to the development backend, so it adds no new distribution.
- **No crash reporting (a named substitution).** Headless mode runs the no-op crash reporter, even when a `SENTRY_TEST_*` variable asks for Sentry (`DependencyContainer.forcesNoOpCrashReporter`, AIA-0991). The build keeps its DSN; a Debug build never starts Sentry without `SENTRY_TEST_*` anyway, so the `SENTRY_DSN=` the old headless build passed only changed what the handshake reported. The handshake's `crashReporting` now reports the reporter actually in use, and ProjectTool (`MLBrowserHeadless`) refuses to drive a process that says anything but `false`.
  - Why: Sentry's "Github Alert" rule has no environment filter, so the first error-level event from any environment, development included, opens a GitHub issue. Scenarios provoke failures on purpose, and a flaky soak would file issues.
  - How to remove it: once that rule ignores the `development` environment, drop the headless-mode force in `DependencyContainer` together with `MLBrowserHeadless`'s `crashReporting` refusal.
- **Endpoint.** The server publishes to the kit's `HeadlessEndpoint.defaultFile`, `Headless/endpoint.json` in Application Support, inside the app's data container. The kit's launcher (`HeadlessSimulatorLauncher`, run by ProjectTool) reads it there through `HeadlessEndpoint.containerPath` (`xcrun simctl get_app_container <device> com.aiarcheology.ios data`); neither side declares the path itself (AIA-1007).
- **Never production.** Three independent locks keep headless automation away from production data:
  1. Compile time: `AppEntry`'s headless branch, `MLBrowserHeadless` and its command server compile only under `DEBUG && AIA_BACKEND_ENV_development` (an architecture test checks the whole-file wrap of every file that imports the transport or HeadlessKitUI), so neither Release nor a Debug build against production contains a listener. In Release the kit itself compiles to nothing as well (kit 0.2.0, AIA-1006), which the release check's footprint scan confirms on the archive. Such a build ignores `-interface`.
  2. The server refuses to start unless the backend is `development`, and the in-app backend switch refuses in headless mode.
  3. The handshake reports `backendEnvironment`, so a launcher can refuse anything else.
- **Real by default (AIA-0976).** A fresh install enters the way a new user does: real StoreKit, the real Keychain free-access anchor, the free-access Welcome screen, the tour, then the consent question.
  - **The Keychain anchor.** Headless mode uses `KeychainFreeAccessAnchorService`, as a user's install does. A throwaway probe build (never committed) read and wrote the production anchor item at launch on `aia-headless-a`, iOS 27.0 simulator, Xcode 27.2 beta:

    | Step | Anchor at the next launch |
    |-|-|
    | Relaunch | present |
    | Uninstall, reinstall | present: it survives app deletion |
    | `simctl erase` | absent: the device's keychain database is deleted |
    | `simctl keychain <udid> reset` on the booted device | absent |

    So erase alone makes a fresh install fresh on 27.0. The launcher also runs `simctl keychain <udid> reset` after booting a fresh install, as a guard for a runtime that might keep it.
  - **Omissions.** Headless mode does not render the paywall or Welcome views, so it does not do what only they do (these are rows in [Differences from the app](#differences-from-the-app)):
    - It loads no products (`loadProducts()` runs from `WelcomeView`, `PaywallView`, `SettingsView` and `SubscriptionStatusView`), so no scenario depends on the sandbox network.
    - It sends no `paywall.shown`. `welcome.shown` is still sent, from `FreeAccessState.markPromptShown()`.
  - **The foreground entitlement re-check runs here too (AIA-0993).** It moved out of `SubscriptionGateView` into `AppRuntime`, which both entries start, so on every `willEnterForeground` once `AppState` is ready and with the payments surface on, headless mode re-runs `SubscriptionState.start()` as the app does, and logs `Entitlement re-check on foreground` (`.lifecycle`). A scenario still never sees it: a headless run does not go to the background between commands.
- **Screens.** Every screen is derived from `AppState`. The root gate's part comes from `SubscriptionGateCoordinator`, the object `SubscriptionGateView` itself runs on: headless mode owns one, as it has one window, and runs its Debug-only `reconcile()` whenever a command reads the screen or the context once `AppState` is ready, several times per response and on every poll of a `wait route`. That does what the view's `onChange` handlers would, but only while a command runs: an idle headless app raises nothing. The analytics gate's part comes from `AnalyticsChoiceDisplay`. Each action calls the method the UI calls.

  **Shared with the app, and copied (AIA-0984).** The route is decided from the objects the views themselves run on, so the two builds cannot disagree about them:
  - the root gate: `SubscriptionGateCoordinator` (AIA-0976); the analytics gate: `AnalyticsChoiceDisplay`; findings: `FindingRepository`; back-up: `FindingsSyncCoordinator`; the drawer: `AppChromeState.presentedSideMenu`;
  - the drawer's sheets: `DrawerPresentation` (the findings list, the sign-in sheet and Settings), owned by `AppChromeState`. The drawer binds its `.sheet`s to it. What the footer offers in each auth context is its `accountOffer(for:)`, which the footer draws and `open-account` follows, and the tap is its `presentAccount(_:usesRealAuth:)` (AIA-1003). Closing the drawer dismisses them in `presentedSideMenu`'s `didSet`, which is what unmounting the drawer did to its `@State`;
  - opening the findings list: `FindingsSyncCoordinator.activateFindings(directory:)` sweeps orphaned screenshots and starts a sync, called by the list's `onAppear` and by `open-findings`, which passes the screenshot directory its parts name (AIA-1003);
  - the web screen's sheets: `SaveFindingPresentation` (the save sheet's capture and the sign-in offer that follows a signed-out save), owned by `AppChromeState`. `StagedImageCapture` writes the same capture, and the offer's decision is its `offerSignInIfEarned`, called by the web screen and by `save`.

  **Controls headless does not know about (AIA-1003).** `ControlCoverageTests` (run by Harmonize) scans `UI/`: every interactive `Testability` control written as a literal in a view with a headless counterpart maps to a `HeadlessAction` name declared under `Headless/`, or carries a reason; every other area of `UI/` is declared uncovered once, by directory. A new control on a covered view, or a view in a new directory, fails until it is declared. Its limits: a new file inside an already-uncovered directory passes (by design, to keep the list short); an identifier passed through a parameter (`ConsentCard`, `FloatingNavBar`) is checked only where its literal is written; a control with no identifier is invisible; and an action only has to exist on some headless screen, not the matching one.

  Two things remain copies, each with its reason:
  - `hasEverShownAnalyticsContent`, `AnalyticsChoiceGate`'s memory of having rendered its content, is `@State` in that view and is kept by `MLBrowserHeadlessApplication`. It is per-window render memory, set by the gate's own `onChange`, which headless mode has no view to run.
  - The layer order. Which screen is on top follows from where each view sits in the tree, so it cannot be driven from a declaration. `HeadlessRouteDecision.route` declares it once (see the deviations below), `HeadlessRouteDecisionTests` pins it, and the parity test (below) checks it against the app.

  The table describes the routes; it is not their source. The source is the navigation map below, which `exec map` prints.

  | Route | Shown when | Actions |
  |-|-|-|
  | `launching` | `AppState` is not ready | none |
  | `gate` | the hold while the free-access window is still being read | none; `state` shows the gate inputs |
  | `paywall` | the wall, or the wall over the app after access ran out mid-session | none. Purchasing needs a real App Store purchase, and restoring would raise the App Store sign-in; the paywall's other controls (sign in, sign out, delete account, export or remove findings) are not offered either. `state` is `{isSubscribed, expired}` |
  | `welcome` | the root gate raised a Welcome screen: the free-access offer, or the payments-off introduction | `continue`, with no declared destination: the response's `route` is the tour when one is owed, otherwise the consent question or `home`. `state` is `{offer: freeAccess, days}` or `{offer: introduction}` |
  | `tour` | the onboarding tour is armed or running | `skip` |
  | `consent` | the analytics question is on screen, or held (`state.pending`) | `allow`, `deny` (none while pending) |
  | `home` | the app proper, menu closed | `open-drawer` → `drawer` |

  `home` also offers `detect-image image=<staged name>` when the launch staged an image, and `pick detection=<index>` → `save-finding` while a detection pass is held. `drawer` also offers `open-findings` → `findings`.

  `drawer` state lists the menu's own models, from the same fetch as the view: `{id, name, type, enabled, canEnable, loaded}`. `account` state is `{signedIn}`, plus `backUpEnabled` while signed in with a Worker. The wait conditions are `ready`, `model-loaded id=…`, `signed-in`, `backed-up id=…`, `finding-present id=…`, `finding-absent id=…`, `access-ended` (the root gate walls: `wall` or `wallOverContent`), and the built-in `route route=…`. `context.gate` reports the gate inputs with every response, including the root gate's `display` (`content`, `wall`, `wallOverContent`, `hold`) and the raised `welcome` (`freeAccess`, `introduction` or null). `context.analytics.enabled` reports whether analytics is actually on: the user's answer under the live flag. `context.auth` reports `gate`, `usesRealAuth`, `signedIn` (a validated account) and `accountPresent` (Clerk itself still holds a user, so a sign-out can be proven to have ended the session). It never reports the email address or the account id.
- **Navigation map (AIA-0982, AIA-0983).** `HeadlessNavigationMap.declaration` (`ios/MLBrowser/iOS/Headless/HeadlessNavigationMap.swift`, Debug only) declares every `HeadlessRoute`. It is built by an exhaustive `switch`, so a new route does not compile without a declaration. `MLBrowserHeadlessApplication.navigationMap` returns it, and the handshake's `routes`, the session's route rejection and `map` all come from it.
  - It declares literal transitions (`home` `open-drawer`, `drawer` `close`, `open-findings`, `open-account`, `home` `pick`), the state-dependent exits of the sheets (`account` and `findings` `close` and `save-finding` `cancel` and `save` land on `drawer`, `home`, `backup-consent` or `paywall`; `save` also on `account`, the sign-in offer), action-driven edges with no `navigatesTo` (`welcome` `continue`, `tour` `skip`, `consent` `allow`/`deny`, `sign-in`, `sign-out`, `save`, `backup-consent` `accept`/`decline`), and the moves the app makes on its own: out of `launching` and `gate`, onto the paywall when access runs out and off it when access returns, and onto `backup-consent` when a sync raises the question. Actions that stay on their route (`enable`, `refresh`, `set-backup`, …) are not declared.
  - **The checked-in copy.** `ios/HeadlessScenarios/Map/navigation-map.json` is the declaration, pretty-printed with sorted keys. `test --lint` and `test`'s pre-build check read it, so neither needs a build. It sits in a subdirectory so that `test` does not take it for a scenario.
  - **Keeping it equal.** `HeadlessNavigationMapTests.test_theCheckedInMap_isTheDeclaration`, in the unit test plan, fails when the file's decoded value differs from the declaration. It reads the file as a resource of the unit-test bundle, because Xcode Cloud runs prebuilt tests without the checkout, and a missing resource fails the test rather than skipping it. To regenerate the file, run that test: its failure message prints the new content, and it also writes it to `navigation-map.json` in the simulator's temporary directory. Replace the file with it. A missing, undecodable or empty file fails `--lint` and the pre-build check, naming this test.
  - **Auditing the map with the app's own moves off (AIA-0994).** Repeat this whenever the map changes: `scripts/headless.sh test --app-moves off` (it prints a banner, and refuses an app whose handshake does not echo `appMoves: off`, relaunches included). Every failure is then an `undeclaredTransition` that is either a missing declaration (declare it and regenerate the checked-in copy) or a real race the one-hop rule absorbs (name it here). The gate is the default run, with the hop on; the audit is not.
    - Audit on AIA-0994 (2026-09-28): all 19 scenarios passed with the hop off, so the map needed no new declaration and no run hit a race the hop absorbs. The one-hop rule still matters for races the suite does not provoke every time, such as `open-drawer` while access runs out.
    - Removing one `sign-in` exit (`→ drawer`) fails `backup-off` with the hop off (`declared: paywall, consent, home, backup-consent; accepted after the app's own moves: none (app moves off)`) and passes with it on. Removing the `drawer`, `consent` and `paywall` exits fails it with the hop on (`declared: home, backup-consent; accepted after the app's own moves: paywall, consent`).
  - **The app's own moves, classified (AIA-0994).** Every action-less edge comes from one of these, and `test_movesOnTheAppsOwn_areExactlyTheDeclaredActionlessEdges` checks each against `HeadlessRouteDecision`: `AppState` becoming ready; the hold lifting once the free-access window is read; access running out (the window closing, or the foreground entitlement re-check finding no subscription) or returning (a subscription arriving, or the re-check finding one); and a sync raising the back-up question. The foreground re-check (AIA-0993) runs from `AppRuntime` in headless mode too, but only on `willEnterForeground` once ready, and a headless run never goes to the background, so it cannot fire in a run. If it did, it would only restart `SubscriptionState.start()`, whose one route effect is the root gate's display between `content` and `wall`/`wallOverContent`: moves already declared.
  - **Drift tests.** `HeadlessWalkTests` drives a real `MLBrowserHeadlessApplication`, built on isolated parts, through `InProcessDriver` over the states the scenarios reach: from launching through the gate, `welcome`, the tour and the consent question to `home`, the drawer, `account` (anonymous and signed in, with `sign-out`), `findings` and `save-finding`, plus `paywall` and the payments-off introduction. At every state, every offered transition must be in the map (`map`'s `undeclared` is empty), and every move, by an action or on the app's own, must be a declared edge. The Tier 1 tests in `HeadlessNavigationMapTests` enumerate the reachable states of `HeadlessRouteDecision`. Every sheet's `close`, `cancel` and `save` lands on one of its declared exits, and every declared exit is where some state lands; `save` may also land on `backup-consent`, which its sync can raise, and on `account`, the sign-in offer. Every route change the app makes on its own, from access running out or returning, the hold lifting, a sync raising the back-up question or `AppState` becoming ready, is a declared action-less edge. Every declared action-less edge is produced by one of those changes or listed in the test, with its reason, as not modelled.
  - **Not walked.** `sign-in`: mock auth refuses its handler, so its edges are declared by hand and only `sign-in-sign-out` exercises them. `backup-consent`: reaching it needs a finding saved before sign-in and an account change through sync, and the walk saves nothing and cannot sign in. The Tier 1 test covers the edges into it; its `accept`/`decline` edges are declared by hand. The walk never performs `save`, because the screenshot store writes to the app's real Documents directory.
  - Examples: `scripts/headless.sh exec --state a map` prints the JSON. `scripts/headless.sh exec --state a --format dot map | dot -Tsvg -o map.svg` draws it: the current route is filled, open edges are green, available ones blue, the app's own moves dashed, and undeclared live transitions red. The `--format` option goes before the command, because everything after the command is passed to the app.
- **Signing in.** `sign-in` goes through Clerk's own API against the development instance: an email-code sign-in, or a sign-up first when Clerk does not know the address, then the gate refresh the app's sign-in sheet runs (see [AUTH-SUBSCRIPTION.md](AUTH-SUBSCRIPTION.md#signing-in-without-the-ui-debug-only-aia-0974)). No auth mock is involved. The action returns once the app holds a validated account, then closes the account screen as the sheet does; the account's own analytics question may then take the screen. `sign-out` calls `AuthState.signOut()`, the paywall's call, and closes the account screen as Settings does. It fails with `actionFailed` if Clerk still holds the session afterwards: the app signs a user out locally even when Clerk's request fails, but automation must not treat that as a clean sign-out.
  - It refuses to run on mock auth (a Debug build without Clerk keys) with `actionFailed`, so a keyless build cannot pass a sign-in scenario without reaching Clerk. `context.auth.usesRealAuth` says which a run got.
  - It accepts only **Clerk test addresses** at the reserved domain, `<name>+clerk_test@example.com`, and refuses anything else with `invalidArgument` before any request. It also refuses to run unless the build points at the development backend. Clerk's test mode sends these no email and accepts the fixed code `424242` ([Clerk docs](https://clerk.com/docs/guides/development/testing/test-emails-and-phones)). A failure reports Clerk's error code only, never text that could echo the address.
  - **The automation account** is `aia-headless+clerk_test@example.com` with code `424242`, committed in `sign-in-sign-out.json`. Both are Clerk's documented test values, not credentials. The account is **permanent** and exists **on the development instance only**. It was created once through Clerk's sign-up, with the names Headless Automation and a discarded random password. Because the development publishable key ships in every Debug build and test mode accepts `424242` for any test address, anyone holding that key can sign in as this account. It must **never hold real data**.
  - **The sign-up branch is not soaked.** The account already exists, so every scenario run takes the sign-in branch. To re-verify sign-up: `headless.sh exec --state a perform sign-in email=<new-name>+clerk_test@example.com code=424242` on a signed-out installation, then delete that user through Clerk's API. Sign in to it with the email code (native Frontend API: create a sign-in with strategy `email_code`, attempt code `424242`), then `DELETE /v1/me` (the instance allows self-deletion). A new sign-in attempt must then return `form_identifier_not_found`.
  - **Sessions.** A successful run signs out, which removes its Clerk session. The `sign-in-sign-out` teardown signs out from wherever a failed run stopped, as `bestEffort` steps. Its `deny` is skipped `unless` the consent question is on screen (`notRoute` `consent`), and its `sign-out` is skipped `unless` Clerk still holds a user (`/context/auth/accountPresent`), so a green run prints no warning. A run that dies while auth is still resolving, with a user present but no account action offered, still sends `sign-out`, and the `unknownAction` warning it prints is the signal: that run leaves one session on the automation account until Clerk's session lifetime expires it or someone revokes it: sign in to the account through the Frontend API, `GET /v1/me/sessions/active`, then `POST /v1/me/sessions/{id}/revoke` for each.
  - Headless mode mounts no `ClerkSessionWatcher`, which is a view. A session revoked on the server during a run is noticed only at the next foreground re-validation. A headless run never goes to the background, so within a run it is never noticed. For the same reason neither headless mode nor the parity test can show #987's class of sign-in race.
- **Finding, saving, backing up (AIA-0975).** Only the picture is staged. Detection, persistence, upload and sync run the app's real code against the development findings Worker.
  - **Detecting.** `detect-image` runs `DeepDrivers.detect(on:tiling:)` with the enabled models and the app's tiling setting, then `DetectionPresentation.filteredFrame`: the two calls the web screen's detection coordinator makes. This happens in `StagedImageCapture`, a Debug-only State object; Harmonize keeps UIKit out of the adapter.
    - The result is `{detections:[{index, label, confidence}]}`, flattened in driver order, then observation order. It carries no boxes, image data or paths.
    - Vision output can vary with the compute unit, so scenarios assert at least one detection (`exists /result/detections/0/label`), never a count or a box.
  - **Saving.** `pick` builds the `FindingCapture` the web screen builds for a tapped detection, with no page URL. `save` calls `FindingRepository.save(capture:cropRect:metadata:)`, the save sheet's own call, with the author taken from the account's display name when the sheet opens (at `pick`), as the web screen seeds the sheet.
    - `save` returns `{id}` (the finding's `entityId`, the id every installation shares) once the sync cycle the save triggered has finished.
  - **The findings screen** lists the Findings sheet's own fetch: all ready findings, newest first. That includes received findings; the UI opens on its Mine tab.
    - Each finding is `{id, title, backup, hasImage}`, where `backup` is `backedUp`, `owed`, `keptOnDevice` or `none` (no ledger opinion, for example signed out).
    - The state also has `usage` (`{used, limit}` or null), `pendingUploadCount` and `parkedCount`.
    - Opening it does what the sheet's `onAppear` does: the orphan sweep, then a sync cycle, awaited.
  - **Every action that starts a sync returns once that cycle has finished:** `save`, `delete`, `refresh`, `synchronize`, `set-backup`, `accept` and `decline`.
    - `synchronize` returns `{outcome: succeeded|offline|quotaFull|failed}` from the button's own outcome line. It fails with `actionFailed` when no synchronize ran.
    - `remove-all-findings` returns after the local removal, as Settings does. Its tombstones go out on the next cycle.
  - **The back-up question** is raised in the middle of the cycle that sign-in sets off. Reach it with `wait route=backup-consent`, never by expecting the route in the `sign-in` response.
    - A sheet's `close`/`cancel` declares `backup-consent` as its destination when the question is pending, because that is where closing the sheet lands.
  - **Deviations from the app, by design:**
    - Headless mode saves the **whole staged image**. The save sheet's crop editor frames the image from its on-screen viewport, which does not exist here, so `save` passes the unit rect to `FindingCapture.cropped(to:)`, which returns the image unchanged for it: no crop code runs, and the full frame is stored and uploaded.
    - **WebScreen is unchanged.** Its detection pick already lives outside the view (`FindingCapture.detection(at:…)`, `detectionAlignedWithCentre`). The rest of its capture path (snapshot provenance, location resolution) is browser-bound and out of scope.
    - After a save, the sheet also records the tour step and a review-prompt moment. `save` does neither: they are UI bookkeeping, not persistence.
    - `save` offers sign-in as the web screen does once the save sheet closes on a saved finding, through the same decision (`SaveFindingPresentation.offerSignInIfEarned`): signed out, outside the tour, and only the first time (`signInOfferShown`). The web screen offers it only when the review prompt stays quiet. Headless records no review moment, so it models the UI-test environment, where the review prompt is suppressed (`DependencyContainer.reviewPromptCoordinator`). In a plain Debug run of the app the review prompt can take that dismissal instead, and then no offer is shown.
    - The route follows the app's layer order, declared once in `HeadlessRouteDecision.route` (AIA-0984; it replaced #974's order, where the analytics question outranked a sheet). Top to bottom: a sheet, while the view presenting it is mounted; the back-up question, which the analytics question on screen holds; the root gate (hold, wall, paywall over the app, Welcome); the analytics gate (its choice or hold, or its question over content); the tour; the app proper. `HeadlessRouteDecisionTests` pins it, and the parity test checks it against the app (see [Parity with the app](#parity-with-the-app)).
  - **The second automation account** is `aia-headless-other+clerk_test@example.com` with code `424242`, for `foreign-findings-stay-local`. It is Clerk test values again, development instance only, and never holds real data. It was created once through the app's own sign-up branch (`headless.sh exec … perform sign-in` on a signed-out installation), so no soak run takes sign-up.
  - **Server data.** The development Worker (`aia-findings-staging.vladimir-slavik.workers.dev`) is shared by both accounts across every run. Its R2 storage counts against the same free allowance as production. So:
    - **Known-empty start.** After its first sign-in, each scenario checks through a successful `synchronize` that the account holds exactly what the scenario expects: no live rows, or only the finding it is about to consent to.
    - **Teardown owns the cleanup.** It uses ordinary steps, so a green run is a clean run. The installation that created rows runs `synchronize`, `remove-all-findings`, then `synchronize` again, which must report `succeeded` with no rows. The account that owns the rows sends the tombstones. In `foreign-findings-stay-local`, whoever is signed in last (Y) cleans first, so a regression that uploaded X's finding to Y leaves nothing behind. X then signs in to send the tombstones queued for X. Every installation that signed in signs out. Navigation steps are `bestEffort`, because a failed run can stop anywhere.
    - **Warnings on a green run.** Every teardown action that can have nothing to do carries `unless`: `deny` (`notRoute` `consent`), `cancel` (`notRoute` `save-finding`), `close` (neither `findings` nor `account`), `decline` (`notRoute` `backup-consent`). `HeadlessScenarioPolicyTests` fails a best-effort teardown action without one. The navigation `goto`s stay plain `bestEffort`: reaching the current route is already a no-op, and a failed run can stop where the drawer is unreachable (the paywall). The **only** warnings allowed on a green run are the five advisory `usage.used == 0` observations (below), and only when the Worker still holds a byte reservation: that is a real signal, not noise, and the observation sends nothing, so `unless` does not apply. Any other warning means a cleanup did not happen.
    - **Rows are the gate; bytes are advisory.** The Worker charges bytes before each R2 write and reclaims an uncommitted upload only after 24 hours. After a crash between an image upload and its metadata, `usage.used` can stay above zero with no row behind it. The teardown therefore checks `usage.used == 0` only as a `bestEffort` step.
    - **Recovering a dirty account.** If a scenario fails its known-empty check, sign in to that account with `headless.sh up`/`exec`, open findings, `synchronize`, `remove-all-findings` on the account screen, then `synchronize` again.
    - **Residual risks.**
      - A row imported by a concurrent pull between `remove-all-findings`' id snapshot and its batch delete loses its tombstone. The teardown's own `synchronize` does not see it, because the pull's cursor has already passed it. The next run's known-empty check on a fresh install catches it, and the recipe above clears it.
      - A pull halted by a retryable download error still reports `succeeded`.
    - **Tombstones stay.** Deleted rows remain in the index forever, and every fresh install pulls them, so the index grows slowly with each run.
      - To reset an account completely, sign in to it through Clerk's Frontend API and delete the user (`DELETE /v1/me`). The Worker's `user.deleted` webhook purges that Clerk user id's data.
      - Signing in with the same address afterwards creates a new user with an empty namespace. Scenarios name only the address.
    - **Never call the Worker's account-erase route (`DELETE /v1/me/data`) from automation or by hand.** It fences the Clerk user id permanently, and every later write for it fails with `410 account_deleting`.
- **Tooling.** `scripts/headless.sh` wraps `ProjectTool headless`, which is the kit's `headless` command line (`HeadlessTool`) run with ML Browser's project, `MLBrowserHeadless` (see [Where the host side lives](#products-the-headlesskit-package)). `scripts/headless.sh help` lists the commands and options:
  - `build`, the Debug app's build (`unittest.sh`'s; not needed right after it)
  - `up --state a [--flag key=true…] [--image <repository path>…] [--free-access-ends-in <seconds>] [--mock-subscription subscribed]` (the mock is manual-only; see Launch options)
  - `exec --state a [--format json|dot] <command>`, for example `exec --state a perform enable id=…`, or `exec --state a --format dot map` (`dot` renders only `map`; options go before the command). `name=value` is text; `exec` converts it to the declared type (AIA-0992): for `perform` it asks for the screen's actions first (a `state` request), for `wait` `help`'s conditions. It never guesses from the text, so `title=2024` stays a string, and `pick detection=0` sends the integer `0`. A value that is not the declared type (`enabled=yes`, an integer beyond ±2^53−1) fails before anything is sent; an undeclared action or parameter is sent as text for the app to refuse. Without arguments, no extra request is made.
  - `down --state a`, and `reset --state a`, which erases the device and resets its Keychain
  - `up` and `test` take `--app-moves off` for the map audit (see Navigation map); every launch of that run, relaunches included, then accepts only declared transitions
  - `test [--no-build] [files…]`, which runs every `ios/HeadlessScenarios/*.json` by default, after the static route check; `--no-build` uses the product already there, for example right after `unittest.sh`
  - `test --lint [files…]`, which runs only the static route check: no build, no simulator

  It creates and uses only simulators named `aia-headless-<state>` and never touches any other device. `build` makes `unittest.sh`'s build in its DerivedData (see [which builds share one binary](#ml-browsers-headless-mode)), and every launch passes `-interface headless` ahead of the scenario's options. A scenario's first launch of an installation erases its device and resets its Keychain, making it a fresh install. A freshly erased device can refuse `simctl install` and `simctl launch` for a few seconds after it reports booted, so the tool retries each up to five times, two seconds apart, and prints every retry. `relaunch` keeps its data and does not reinstall. Reinstalling moves the app's data container, and preference writes the system has not yet flushed would be lost with the move. A relaunch quits the app the way a force-quit does, so a preference written in the moment before it can still be lost, as on a device.
- **Things a run cannot control:** remote `appMessages` can change during a run, and a live message may raise a notification-authorization alert on the device. Neither may be asserted.
- **Analytics signals from automation.** `consent-allow-persists` chooses `allow`, so every run of it sends the buffered funnel (`free_access.window_granted`, `welcome.shown`, `free_access.continue_tapped`, onboarding) to TelemetryDeck: anonymous, about ten runs per soak. The SDK marks every signal from a Debug build as test mode, and there is one app ID. This is kept on purpose, not substituted: blanking the app ID would let the scenario pass with analytics never activating. If the owner prefers no test signals at all, the alternative is to blank the app ID in headless mode at runtime; blanking `TELEMETRYDECK_APP_ID` in the build would split headless mode's product from `unittest.sh`'s (AIA-0991). The scenario would then need a store-level check instead of `context.analytics.enabled`.
- **Error codes.** `error-contract` provokes, against the real app, `unknownAction`, `unreachable`, `unknownCondition`, `timeout`, `actionFailed` (`detect-image` on the committed text file `ios/HeadlessScenarios/Fixtures/not-an-image.png`) and `invalidArgument`, and checks that the app still works afterwards. `malformedRequest`, `unknownCommand`, `unauthorized`, `protocolMismatch` and `busy` cannot be written in a scenario, nor can `undeclaredTransition` against an adapter that matches the app; the HeadlessKit tests cover them.
- **Soak notes.** A `relaunch` right after a preference write can lose it, as a force-quit can on a device. The sensitive step is in `onboarding-interrupted`: a relaunch right after `skip`, whose write is `TourState.markSeen()`. If it is lost, that installation shows `tour` where `consent` is expected.

### Debugging headless mode in Xcode

The MLBrowser scheme has a disabled launch argument, `-interface headless` (Edit Scheme › Run › Arguments).

1. Create the device once, for example with `scripts/headless.sh up --state a`. Xcode's run destination must be an existing `aia-headless-<name>`: `exec` finds the app's endpoint by that device name only.
2. Tick `-interface headless`, pick `aia-headless-a` as the run destination, and Run. Breakpoints work as in any Debug run.
3. Drive it from a terminal: `scripts/headless.sh exec --state a state`, `exec --state a goto drawer`, and so on.
4. Untick the argument before running tests: the scheme hands it to the test hosts, which then stop at launch.

How it differs from `up`:

- Run applies the scheme's `Configuration.storekit`, so StoreKit answers from that local configuration, not from the sandbox a `simctl launch` reaches.
- The scheme passes no headless options: flags follow ConfigCat's Test environment unless you add `-headlessFlag key=value` arguments. `detect-image` accepts only images the launch names: copy one into the container first (an earlier `up --image <path>` leaves it in `Library/Application Support/Headless/Staged/`) and add `-headlessStagedImage <file name>` to the scheme's arguments.
- Run installs Xcode's own product on the device (see [which builds share one binary](#ml-browsers-headless-mode)); the next `up` reinstalls the shared one.

### Differences from the app

- **Equivalent:** the same production operation as the UI.
- **Projection:** the UI's representation is removed and the semantics are kept.
- **Substitution:** a different implementation, used on purpose.

### Parity with the app

The parity test (AIA-0984) checks that the app and headless mode reach the same screens, in the same order, for the flows most likely to drift. It is a guard, not a second suite, and it runs **locally only**: no CI job runs it.

- **The flows.** Four scenarios, `ios/HeadlessScenarios/parity-*.json`: `parity-onboarding` (fresh install → Welcome → tour → consent → home), `parity-sign-in` (sign in and out through Clerk's development instance), `parity-save-finding` (save a finding while signed out, which raises the sign-in offer) and `parity-paywall-over-sheet` (access runs out while the findings list is open; the list stays on top, and closing it lands on the paywall).
- **One declared sequence, two legs.** Each scenario is the declaration: a step carries at most one `route` expectation, and a step whose landing is asynchronous (`sign-in`) carries none, with the following `wait` carrying it.
  - The headless leg is the scenario itself: `scripts/headless.sh test ios/HeadlessScenarios/parity-*.json`. They are ordinary scenarios, so every full `headless.sh test` runs them too.
  - The UI leg is `HeadlessParityUITests`, in its own `HeadlessParity` test plan. It reads the same four files from its bundle, drives each flow by hand with one step closure per scenario step (a `wait route` step's closure runs that wait: it polls, within the step's timeout, until the named route is on top), records the screen on top after every step that carries a route, and fails with both lists when the recorded sequence differs from the scenario's. The Clerk test address and code come from the scenario's `sign-in` step, never from the test source.
  - Comparing each leg with the one declaration, rather than diffing two recorded logs, needs no file passing between the simulator runs, and a change on either side still fails: a headless change fails the scenario, an app change fails the UI test, and editing the scenario to match one side fails the other.
- **How the UI leg reads the screen.** Each route has a probe, an accessibility identifier on that screen. After a step, the recorder waits until the set of hittable probes has been stable for about 1.5 s. Exactly one hittable sheet or overlay probe is the screen; with none, exactly one of `home` and `drawer` is. Anything else fails, naming the set. The only order the recorder assumes is that the app proper lies beneath every overlay and sheet, which holds by construction; it never orders overlays or sheets against each other, so the stacking the test exists to check stays observable. It never knows the expected route.
- **What it guards.** The copied layer order (above). Moving the paywall above the sheets in `HeadlessRouteDecision.route` makes `parity-paywall-over-sheet` fail, because headless mode then reports `paywall` while the app still shows the findings list.
- **Launch mapping.** The UI leg launches with the scenario's flags as `featureFlagOverrides`, the tour armed, the analytics question unanswered, `-mockSubscription notSubscribed` (headless mode runs real StoreKit, which reads as not subscribed) and signed-out mock auth, except `parity-sign-in`, which sets `usesRealAuth`. `parity-paywall-over-sheet` passes the scenario's `freeAccessEndsIn` as `freeAccessEndsInSeconds`. Parity is by route only: the UI leg's tour does not stage the demo page, and its save may take the red-crosshair path.
- **Two Debug-only hooks it needs**, each a named launch option:
  - `UITestLaunchConfiguration.usesRealAuth` selects the real Clerk provider in a UI test, which otherwise always runs on the mock. It traps without a `pk_` key or off the development backend, so it never falls back to the mock. Why: the sign-in flow must go through Clerk's own `AuthView` and `UserProfileView`. How to remove it: delete the field, its input to `DependencyContainer.authProviderSelection` and `parity-sign-in`'s UI test.
  - `freeAccessEndsInSeconds` / `-headlessFreeAccessEndsIn`: see Launch options.
- **Running it.** Run the two legs one after the other, never at once: they share one Clerk account and the development Worker.

  ```bash
  scripts/headless.sh test ios/HeadlessScenarios/parity-*.json
  xcrun simctl erase <runner-udid>
  xcodebuild test -workspace ios/MLBrowser.xcworkspace -scheme MLBrowser \
    AIA_INCLUDE_TEST_FIXTURES=YES -testPlan HeadlessParity \
    -destination "platform=iOS Simulator,id=<runner-udid>" -derivedDataPath "$PWD/.deriveddata"
  ```

  The UI leg needs the Clerk keys and network access, and takes a few minutes, two of them waiting for free access to run out. The Clerk session survives the UI tests' data wipe in the Keychain; the flow signs out at its end, and erasing the simulator first covers a run that failed midway. `MLBrowserUITests` skips `HeadlessParityUITests`, so the regular UI suite stays offline.

## Compatibility

`Command`, `Expectation`, and the error-code set can grow. Adopters should not switch over them exhaustively without a `default`. New protocol fields are always optional. A change that an older peer would misread bumps `HeadlessProtocol.version`, and the handshake then rejects the mismatch.

Protocol v1 is not frozen until the AIA-0970 chain merges, so these changes stay v1 (AIA-0992):
- **One controller.** A second hello gets `busy` and is closed; before, two clients could drive one app.
- **Strict wire types.** Text for an `integer`, `number` or `boolean` parameter, and a number or boolean for a `string` one, is `invalidArgument`; before, the session converted them. A client that sends native JSON types is unaffected; `headless.sh exec` converts its text itself.
- **Declared transitions (AIA-0994).** Every action is checked against the map, and a miss is the new `undeclaredTransition`. An app with an **empty map** keeps its only check, a set `navigatesTo` reached exactly, but a miss is now `undeclaredTransition`, not `actionFailed`; an adopter that matched on `actionFailed` for it must match the new code.
